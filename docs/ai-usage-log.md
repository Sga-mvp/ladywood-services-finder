# AI Usage Log

This document records every meaningful use of generative AI tools during the
project. It supports the AI-declaration slide in the final presentation (5%
of the module mark) and provides transparency about which parts of the work
involved AI assistance and which did not.


Entries are in reverse chronological order (newest at the top).


## 2026-06-08 — Claude (Anthropic), session 3

**Used for:** Resident-facing route handlers (`src/routes/search.py`), Jinja2
templates (`search_results.html`, `service_detail.html`, an
updated `base.html`). Then in the same session,
the admin-facing route handlers (`src/routes/admin.py`), three admin templates
(login, list, edit), an admin-creation CLI helper (`src/create_admin.py`),
and `tests/test_admin.py`.

**Why:** Routes, templates, and CSS for a Flask app are well-trodden territory
where AI assistance accelerates writing without changing the substantive
engineering. The architecturally meaningful decisions. Flask blueprints
keyed to feature areas, server-rendered templates with no JavaScript
dependency on the resident flow, session-based authentication with a
`login_required` decorator, the eligibility booleans on the result cards,
were made by me by reference to the user stories and the class diagram.

Tests were generated alongside the code with explicit Given/When/Then
acceptance criteria from `docs/user-stories.md` as the source of truth. I
checked the tests against the user stories one-by-one before running them.

**What was kept:** The generated route handlers and templates were used
largely as-is after I reviewed them in the browser and ran the tests. One
real bug was caught by the test suite during this session, the service
detail template crashed when a service had no opening-hours rows at all
(empty list). I fixed it by changing the Jinja2 template to handle the
empty case, then re-ran the tests to confirm.

**Not used for:** The user-facing copy on the homepage and result pages
("What do you need today?", the explanatory text on the empty-state, etc.)
was reviewed and approved by me as appropriate for the personas.
 The colour palette in the CSS was generated by me as well as the home 
 page with minimal help from Claude, only used to debug a small issue.

## 2026-06-07 — Claude (Anthropic), session 2

**Used for:** Web-research and assembly of the
seed-loader script (`src/seed_loader.py`), and an update to `src/app.py`
to wire up Flask-SQLAlchemy properly. 

**Why:** Search-engine research on Birmingham community services for the
seed data was significantly faster with AI assistance than reading
individual organisation websites — Claude searched and synthesised, I
verified the most important details by checking the cited source URLs.
SQLAlchemy boilerplate (column declarations, relationship configurations)
is template-like work where AI helps more than hurts.

The data model is a direct translation of my class diagram (which I drew
based on my MoSCoW analysis); no design decisions about the model were
delegated to Claude. The implementations of `Service.is_open_at` and
`OpeningHours.covers` follow the activity diagram I drew.

**What was kept:** Seed data was used as-is after I confirmed each cited
URL was real. Two services I had to push back on — Claude initially
included "Birmingham Digital Support Hub @ Ladywood Leisure Centre" and
"Ladywood & Nechells Advice Service" without verifying they exist; I
flagged this and Claude removed them rather than fabricating. The final
13 services are all verified against real sources.

The SQLAlchemy code was used largely as-is after I ran the seed loader
and confirmed every service loaded with the expected relationships.

**Not used for:** Choosing which services to include or excluding any,
those decisions are mine (e.g. including Spring Hill Library as `is_active:
false` to demonstrate the problem the project addresses). The UML drawing
itself was done by me in draw.io; Claude provided a few pointers to help 
with flows and definitions. 
Web research was done by me finding (13 real
Birmingham community services with sources cited), the SQLAlchemy data
model in `src/models.py` (five classes matching the class diagram),

## 2026-06-03 — Claude (Anthropic), session 1

**Used for:** Analysing the assignment brief and the EWB design challenge
PDF, shortlisting candidate problems, MoSCoW
analysis (`docs/moscow.md`), and the initial repository scaffolding
(README, .gitignore, requirements.txt, Flask app skeleton, pytest
configuration, GitHub Actions CI workflow).

**Why:** Two efficiency goals. First, summarising and cross-referencing
the EWB brief's eight challenge areas to identify the strongest fit for
a software prototype was faster with AI assistance than reading and
re-reading the PDF. Second, repository scaffolding is well-trodden
boilerplate — Flask app factory pattern, pytest fixtures, GitHub Actions
YAML — where AI generation saves time without affecting the substantive
engineering of the project. The conceptual choices (Flask over Django,
GitHub Actions from day one, the specific test strategy) were made by me
after weighing the options Claude laid out.

**What was kept:**  MoSCoW was
generated with options presented to me for the key parameters (number,
detail level, scope strictness), so the high-level shape of each document
was my choice even where the words came from Claude. The repository
scaffolding was used largely as-is, with the understanding that none of
it constitutes the substantive engineering of the solution, it is
project setup that any tutorial or template would produce similarly.

**Not used for:** Choosing the project direction (that was my decision
after reviewing the shortlist of four candidates), writing the
substantive design rationale, or generating any user-facing content. 
Drafting the initial problem statement (`docs/problem-statement.md`),
 personas (`docs/personas.md`),user stories with acceptance criteria (`docs/user-stories.md`)
